#### ✅ `render()` 初始化调用缺失 (2026-06-03 第5轮)
- **问题**: `render()` 函数定义后从未调用。页面加载时 `phase='create'` 但 `render()` 不执行，导致页面永远显示 "Loading AI Studio Pro..."

#### ✅ `const D.charts` 语法错误修复 (2026-06-03 第5轮)
- **问题**: `const D.charts=[...]` 是无效 JS（`const` 不可用于属性访问）。这是误替换 `CHARS` → `D.charts` 造成的连锁错误
- **修复**: 改为 `D.charts=[...]`（D 已是 `const` 对象，追加属性合法）
- **副作用**: 意外删除了 `D.charts=CHARS;` 归一化行，随后手动修复

#### ✅ `let curEp` → `var curEp` (2026-06-03 第5轮)
- **问题**: `let` 声明的变量不在 `window` 上，HTML onclick 属性无法访问
- **修复**: `let curEp="ep1"` → `var curEp="ep1"`
- **影响**: Episode selector 在 Assets 页可正常读写

#### ✅ `let assetsTab` → `var assetsTab` (2026-06-03 第5轮)
- **问题**: 同上，`let` 导致 Assets Tab 切换失效

- **影响**: Assets Tab 切换正常

#### ✅ 批次镜头点击交互增强 (2026-06-03 第5轮)

## 反思与逻辑

### 关键教训 1: write_file 参数长度限制
- **问题**: 直接调用 `write_file` 写入超大 JS 字符串 (数万字符) 时报 `missing 1 required positional argument` — 实际原因是 content 参数过大导致 JSON 解析超限/无效。
- **正确做法**: 将大型脚本拆分为多个小 Python 脚本 (如 build_phase1.py, build_phase2.py 等)，每个控制在 20KB 以内。
- **未来策略**: 对 >15KB 的内容，改为写入 Python 脚本再执行，或使用多条 `edit_file` 分步注入。

### 关键教训 2: 匹配锚点必须精确匹配实际文件内容
- **问题** (Phase1): `OLD_SHOT_EDITOR` 模式假设了不存在的代码细节 (`if(newTitle&&newTitle!==s.t)` 但实际文件是 `if(newTitle!==null){s.t=newTitle;}`，还有额外的 `newDur` 提示)。导致替换失败。
- **正确做法**: 先 `debug_anchor.py` 查看实际文件内容，再用精确匹配。不要假设代码结构。
- **未来策略**: 每次替换前先用 Python 脚本查看目标片段的实际内容，避免锚点不匹配。

### 关键教训 3: shell command 中的换行符会被解析
- **问题**: Windows `python -c "..."` 命令无法正确处理多行 Python 代码；换行符导致 `IndentationError`。
- **正确做法**: 对于多行 Python 逻辑，写入临时 .py 文件再执行，而不是内联 -c。
- **未来策略**: 所有 >5 行的 Python 代码都写为文件。

### 关键教训 4: 替换后可能产生重复函数定义
- **问题**: `build_phase1.py` 替换 `showShotEditor` 时，新定义替换了旧定义，但其他替换/注入操作可能留下旧版本 (如 `moveShot`, `startBatch` 各出现两次)。
- **正确做法**: 替换后运行 `check_dupes.py` 检测重复函数，然后针对性清理 (保留新版本，删除旧版本)。
- **未来策略**: 每次替换/注入后检查 JS 函数唯一性。最后定义优先，但重复浪费体积。

### 关键教训 5: Windows GBK 编码问题
- **问题**: emoji 字符 (✅, ❌, 🎵 等) 在 Windows 终端输出时触发 `UnicodeEncodeError: 'gbk' codec can't encode character`。
- **正确做法**: 避免在 print 语句中使用 emoji；使用 "OK", "FAIL", "SKIP" 等 ASCII 前缀。
- **未来策略**: 在跨平台脚本中始终使用纯 ASCII 日志输出。

### 成功策略: 分解式多阶段构建
- 将大型功能补全拆分为独立的 Python 构建脚本 (Phase1→Phase2→Phase3)，每个聚焦于特定功能域。
- 每个阶段输出到同一个 `v6_final.html` 文件，形成增量构建管道。
- 优点: 可单独验证每个阶段、易于调试、避免单一脚本过大。
- 步骤: 编写阶段脚本 → 执行 → 验证 → 写入记忆 → 下一阶段。

### 工作流优化
- 复杂文件修改优先使用 Python 脚本 (`.replace()` / 正则) 而非 `edit_file`，因为 script 可以处理上下文敏感的逻辑。
- `edit_file` 适合小范围精确替换 (< 10KB)；Python 脚本适合大规模 (> 10KB) 结构变更。
- 执行顺序: write 阶段脚本 → execute → 验证 (check_dupes / verify macros) → 记录。

### 关键教训 6: HTML 结构完整性检查比 JS 语法检查更重要
- **问题**: 经过多阶段替换/注入后，文件 HTML 结构被破坏——`<script>` 块被 `</script>` 过早闭合，导致 JS 分裂为两个脚本块，CSS 夹在中间。这种错误比括号不平衡更严重，因为浏览器会按顺序解析两个独立的脚本块，导致跨脚本变量引用失败。
- **正确做法**: 每次替换/注入后，检查 HTML 标签匹配（`<script>` 数 == `</script>` 数），且 `</script>` 仅出现在期望的位置（通常是文件末尾附近）。
- **未来策略**: 在构建管道的每一步后，运行 `find_script_tags.py` 确认 `<script>` 和 `</script>` 数量一致且位置合理。

### 关键教训 7: 替换末尾与旧文件结构的衔接
- **问题**: Phase1 替换 (`NEW_SHOT_EDITOR`) 的末尾包含了 `genPrompt`，而旧文件中原来 `genPrompt` 之后紧接着 `</script>`。替换后 `genPrompt` 结束位置 = 旧 `</script>` 位置，导致新文件结构被截断。
- **正确做法**: 替换时不仅要替换目标函数，还要确保替换后文件剩余部分的衔接正确。如果替换内容末尾就是 `</script>` 的位置，应在替换后合并下一段内容（例如将 `<style>` 提到新位置）。
- **未来策略**: 替换前先查看旧文件替换范围前后的上下文（前后各 100 字符），确认替换后不影响 HTML 标签结构。

### 关键教训 8: 验证脚本应覆盖 HTML 结构完整性
- **问题**: 之前只验证了函数唯一性和括号平衡，没有检查 `<script>` 块是否被意外分割。
- **正确做法**: 增加 `verify_html_structure.py`，检查：
  1. `<script>` 数量 == `</script>` 数量
  2. 所有 `<script>` 标签内容完整（没有意外闭合）
  3. `<style>` 块位置合理
- **未来策略**: 纳入构建管道的最终验证步骤。

### 关键教训 9: 字符串上下文中的括号不计入平衡
- **问题**: 用简单 `{}` 计数检查 JS 括号平衡会产生假阳性——字符串模板 (`'...'`, `"..."`, `` `...` ``) 中的括号被错误计入。
- **正确做法**: 括号平衡检查需要排除字符串和正则表达式中的括号。可在验证脚本中使用基本字符串状态机（记录 `'`/`"`/`` ` `` 的开闭状态）。
- **未来策略**: 括号平衡验证作为辅助手段，不应作为唯一判断标准。最终验证应使用浏览器实际执行或 `new Function()` 语法检查。

### 关键教训 10: 替换后代码的编译验证
- **问题**: `build_phase1.py` 替换 NEW_SHOT_EDITOR 后，文件大小/函数数量都符合预期，但没有验证 Script 1 能否通过 JS 编译。事实上新替换的代码包含死代码 `move();`，导致整个内联脚本块编译失败，且无运行时错误提示（脚本块整体跳过）。
- **正确做法**: 每次替换/注入后，对每个 `<script>` 块单独执行 `new Function(code)` 进行语法验证，确保无编译错误。
- **未来策略**: 在构建管道中加入 `validate_scripts.py`，对每个内联脚本块执行 `new Function(block)`，报告语法错误位置。

### 关键教训 11: 浏览器无报错 ≠ 脚本执行成功
- **问题**: 黑屏状态下控制台没有 JS 错误日志。这是因为整个 `<script>` 块因编译错误被跳过，而浏览器不会对内联脚本的编译错误显示在默认控制台（安全原因或静默失败）。
- **正确做法**: 用 `window.onerror` 全局捕获（需在页面加载前设置），或用 `document.scripts[i].text` + `new Function()` 主动验证。
- **未来策略**: 黑屏诊断步骤：①检查 `typeof 函数名` ②用 `new Function(script.text)` 测试编译 ③检查 `<script>` 长度是否异常 ④检查 HTML 结构。

### 关键教训 12: 原始文件结构应先彻底确认再推断问题
- **问题**: 在 Phase1 构建后，我误以为脚本分割是 Phase1 替换导致的，花费大量时间分析 Phase1 替换逻辑。实际上原始 v6.html 已经自带 THREE 个 `</script>` 标签。Should have checked the original file structure first.
- **正确做法**: 在分析构建产物异常时，先阅读原始文件的关键结构（`</script>` 位置），确认哪些是原始特征，哪些是构建引入的变化。
- **未来策略**: 在构建管道的任何步骤之前，先运行 `analyze_structure.py` 记录原始文件的 `<script>`/`</script>` 位置基线。

### 成功策略: 使用 `new Function()` 内联验证
- 通过 `document.scripts[i].text` 获取脚本内容，然后用 `new Function()` 检查编译错误。这可以精确定位语法错误在脚本中的字符位置。
- 结合二分查找可以快速定位错误区域。

### 关键教训 13: `let` 变量不可从 HTML onclick 属性访问
- **问题**: 使用 `let phase='create'` 声明全局变量后，HTML onclick 属性（如 `onclick="phase='dash';render()"`）无法修改该变量，因为 `let` 不创建 `window` 属性。
- **正确做法**: 对于需要在 HTML onclick 属性中访问的全局变量，使用 `var` 声明（或显式 `window.phase = 'create'`）。
- **未来策略**: 在编写单页应用（HTML attribute onclick）时，优先使用 `var` 声明所有和 UI 状态相关的全局变量。或在 JS 中将 onclick 改为 `addEventListener` 绑定。

### 关键教训 14: Python 风格条件表达式在 JS 中不可用
- **问题**: 代码中存在 `("text-green-400' if s.status==='completed' else ...")` 这种 Python 风格的语法，JavaScript 不支持。
- **正确做法**: JavaScript 使用 `condition ? trueVal : falseVal` 三元运算符。
- **未来策略**: 在 JS 文件中永远不要使用 Python 语法。

### 关键教训 15: 即使页面显示但 DOM 未及时更新
- **问题**: 在浏览器中通过 `phase` 变量确认状态改变后，snapshot 仍然显示旧界面，导致误判。实际是 `render()` 函数内部有错误（`D.charts` 不存在），导致渲染中断。
- **正确做法**: 先检查 `render()` 是否执行成功，再断言 UI 状态。使用 `try{new Function(code);return'OK'}catch(e){return e.message}` 验证编译，再用 `render();'ok'` 验证运行时。
- **未来策略**: UI 诊断步骤：① 确认变量值正确 ② 手动调用 `render()` 并捕获异常 ③ 检查 innerHTML 是否被修改 ④ 检查 snapshot。

### 关键教训 17: `const` 暂时性死区 (Temporal Dead Zone)
- **问题**: `const D={..., charts:CHARS};` 定义在 `const CHARS=[...];` 之前。`const` 不会像 `var` 一样提升，且进入暂时性死区，导致 ReferenceError: "Cannot access 'CHARS' before initialization"
- **正确做法**: 确保所有 `const` 引用的变量在使用前已被定义。如果无法保证顺序，使用 `var` 或延迟赋值 (如 `D.charts=CHARS;` 放在 CHARS 定义之后)
- **检测方法**: 在浏览器中检查控制台，页面加载时若看到 "Cannot access 'X' before initialization" 即为此问题

### 关键教训 18: 数据模型升级后的字段名不一致
- **问题**: v5→v6 数据模型升级后，`CHARS` 的角色数据使用了 `refs:{front:1,tq:1,side:1,back:1}` 对象描述四视图参考，但渲染代码中仍使用 v3/v4 的 `views:['front','tq','side','back']` 数组。类似的，`ch.lock` 不存在（替代方案是 `ai.consistency` 或 `ai.lora`）。
- **正确做法**: 在升级数据模型的同时，升级所有引用该数据的渲染代码。如果不确定新数据结构的字段名，先读原始数据定义再写渲染代码。

### 关键教训 19: `browser_use evaluate` 对分号敏感
- **问题**: `evaluate("phase='script';render()")` 报 `SyntaxError: Unexpected token ';'`。因为 evaluate 将代码包裹在表达式上下文中，分号会破坏语法。
- **正确做法**: 
  - 使用 `window.varName=value` 赋值 (不需要分号)
  - 每个 evaluate 只执行一条语句
  - 如需多语句，使用箭头函数包裹: `evaluate("(()=>{window.phase='script'; window.render();})()")`
  - 或使用 `run_code` action (但同样有分号问题)
- **区分**: `evaluate` 只接受表达式字符串；若需多个操作应分多次调用

### 关键教训 21: 修复 JS ReferenceError 的完整版诊断流程
- **问题**: 文件内所有全局变量在 HTML onclick 中引用时，需确保它们是 `var` 声明（或 `window.xxx` 显式赋值），否则在严格模式或 `let/const` 声明时无法从 HTML 属性访问。
- **诊断方法**: 

  当页面显示但部分功能不响应时——
  1. 打开浏览器控制台，看有无未捕获的异常
  2. 检查 `typeof 函数名` 确认函数是否存在
  3. 手动调用 `render()` 观察有无异常
  4. 检查渲染函数中引用的全局变量（特别是有 onclick 属性的变量）

### 关键教训 22: 数据模型升级后批量字段名不匹配的修复策略
- **问题**: 数据模型从 `views:[]` → `refs:{}`, `lock:bool` → `ai.consistency:number`, `time:string` → `env.time:string` 等变更，导致多处渲染代码同时报错。
- **最优修复策略**:
  1. 先 grep 所有对新旧字段的引用
  2. 统一修改渲染函数中的数据访问方式
  3. 在数据模型中保留兼容层（如 `get views(){return Object.values(this.refs);}`）防止未来再次遗漏
- **本案例**: 共修复8处字段不匹配，涉及3个渲染函数（renderScript, renderProjectAssets, renderBatch）

### 关键教训 23: JavaScript 字符串转义层级混乱是替换失败的主因
- **问题**: 在 `renderBatch` 函数（一个巨长的 JS 字符串拼接表达式）中查找/替换特定内容时，需要处理多层转义：
  1. HTML 文件的 `&quot;` / `&#x27;` 实体（无此情况，因全部已转义）
  2. JS 字符串字面量中的 `\'` 转义单引号
  3. 拼接变量时的 `+` 运算符
  4. onclick 属性值中的 `\\'`（两个反斜杠 + 单引号）
- **正确做法**: 
  - 先使用 `grep` 或 Python 脚本直接查看文件中的原始字节 (`repr(ctx)`) 确定实际存储的转义形式
  - 然后使用 `edit_file` 的精确匹配功能（不是正则）
  - 对于复杂替换，使用 Python 脚本操作文件（`str.replace()`）更可靠
- **未来策略**: 在含有复杂 JS 字符串拼接的内联 onclick 代码中做替换时，优先使用 Python 脚本按字节操作，避免 `edit_file` 的转义解析问题。

### 关键教训 24: 避免在 `python -c` 中使用多行代码
- **问题**: 多次尝试使用 `python -c "..."` 执行多行 Python 逻辑失败，因为 Windows 命令行将实际换行符视为语句结束（实际上 cmd 的 `-c` 只接受单行参数；换行符会分割为多个命令参数）。
- **正确做法**: 始终将 >1 行的 Python 逻辑写入 .py 文件再执行。
- **未来策略**: 在 Windows 环境下，任何超过 2 行的 Python 代码都写入临时文件执行。

### 关键教训 25: 替换文本中的 BOM 字符预防
- **问题**: Python 文件读写引入了 U+FEFF BOM 字符到 JS 代码中，导致语法错误。
- **原因**: 使用含 `${}` 模板字符串的 JS 代码写入文件时，编辑器或文件系统可能插入 BOM。
- **预防**: 
  1. 写入 JS 代码时始终使用 `encoding='utf-8'` 且不带 BOM
  2. 写入后 grep 检查 `\ufeff` 字符
  3. 避免在 JS 字符串中使用需要转义的 Unicode 序列
- **检测**: `'\ufeff' in file_content` 或 `file_content.count('\ufeff')`
- **问题**: 即使 `phase` 变量已改变且 `render()` 无异常返回，snapshot 可能仍显示旧页面内容。原因是 `innerHTML` 赋值虽然完成但浏览器 DOM 更新可能有延迟，或 snapshot 时机不对。

### 关键教训 16: `document.getElementById('app')` 与 jQuery 的 `$` 冲突

### 关键教训 34: `const` 暂时性死区 (TDZ) 导致页面完全空白 — 最终修复方案
- **问题**: `AI_Studio_Pro_v6_fresh.html` 打开后页面完全空白（无任何内容显示）。

- **正确修复**: 将 `CHARS` 和 `EPS` 的 `const` 声明移到 `D` 之前：
  ```
  // 正确顺序:
  let curEp="ep1";
  const EPS=[...];    // 先
  const CHARS=[...];  // 先
  const D={..., charts:CHARS.map(c=>({...c,views:...}))};  // 后 — 此时CHARS已初始化
  ```

- **未来策略**: 所有 `const`/`let` 声明的初始化顺序必须满足"被引用者先于引用者"。无法保证时改用 `var` + 延迟赋值，或使用 IIFE 延迟初始化。

### 关键教训 41: 自适应布局的"铁三角"原则
- **问题**: 使用 Tailwind 的 `h-screen flex flex-col overflow-hidden` 不一定能在所有浏览器/CDN 环境下工作正常
- **正确做法**: 对布局关键元素使用内联样式 (`style="..."`) 而非 Tailwind 类
- **三栏布局铁三角**:
  1. **顶层容器**: `width:100vw; height:100vh; overflow:hidden; display:flex; flex-direction:column`
  2. **三栏容器**: `flex:1; display:flex; overflow:hidden; min-height:0` ← `min-height:0` 是关键！
  3. **每栏内部**: `display:flex; flex-direction:column; overflow:hidden`，内容区 `flex:1; overflow-y:auto`
- **常见错误**:
  - 忘记 `min-height:0` 导致 flex 子元素不能正确收缩
  - 使用 `h-screen` (100vh) 而非 `100vh` 可能在某些浏览器包含/不包含地址栏
  - 固定宽度导致窄屏溢出
- **未来策略**: 复杂布局使用内联样式 + 严格测试不同视口尺寸

### 关键教训 42: 预览区自适应计算公式
- **问题**: 9:16 画幅预览区固定 360x640 太小或太大
- **正确算法**:
  ```
  containerH = viewportH - 44(顶部) - 40(播放控件) - 60(底部镜头条) - 32(边距)
  containerW = viewportW - 280(左栏) - 340(右栏) - 32(边距)
  // 9:16 比例
  previewH = min(containerH, containerW * 16/9)
  previewW = previewH * 9/16
  ```
- **实现**: 使用 JS 动态计算或 CSS `aspect-ratio: 9/16` + `max-height/max-width`
- **未来策略**: 重要画幅预览使用 CSS `aspect-ratio` 属性 + `max-width:100%; max-height:100%` 容器约束

### 关键教训 43: Tailwind 类的兼容性陷阱
- **问题**: 之前使用 Tailwind 类（`h-screen`、`w-[280px]`）实现三栏布局，用户反馈"UI异常"
- **可能原因**:
  1. Tailwind CDN `cdn.tailwindcss.com` 在某些网络环境下加载失败

  3. `h-screen` 100vh 在 iOS Safari 等移动浏览器包含/不包含地址栏
  4. 复杂组合类 `flex flex-col overflow-hidden shrink-0` 任意一个未应用都导致布局失败
- **正确做法**: 关键布局使用内联样式作为底线保证，Tailwind 类作为渐进增强

  - 内部细节 (padding, color, font-size) 可用 Tailwind 类
  - 任何 `w-[xxxpx]` 任意值类改用 `style="width:xxxpx"`

#### 关键教训 56: `write_file` 工具的 content 参数实际有大小限制
- **观察**: 第三次 `write_file` 写 15284 字节内容时成功, 第四次写 18424 字节时**部分内容被截断**
- **临界点**: 约 15-20KB 是安全范围, 超过有概率截断
- **表现**: 工具返回 "Wrote X bytes" 但实际文件末尾内容缺失
- **验证方法**: 写入后立即 `read_file` 末尾几行, 确认内容完整
- **应对策略**:
  1. 超过 15KB 的内容先拆分到多个文件
  2. 每次 write_file 后用 `read_file` + `tail` 验证末尾完整
  3. 关键内容用 `wc -c` 对比预期/实际字节数

#### 关键教训 57: Windows `cat >> file << 'EOF'` heredoc 命令行长度限制
- **问题**: `cat >> v7.js << 'JSEOF' \n [大量JS内容] \n JSEOF` 失败, 错误 `命令行太长`
- **根本原因**: Windows cmd/PowerShell 在执行 heredoc 时, 将 EOF 标记之间的内容作为单个命令参数传给 shell, 长度受系统限制 (Win10 约 8KB, Win11 略大)
- **正确做法**:
  1. **不要用 heredoc 追加大文件** → 改用 `write_file` 一次性写入完整文件
  2. **用 Python 脚本替代**:
     ```bash
     python -c "with open('v7.js', 'a', encoding='utf-8') as f: f.write(open('extra.js').read())"
     ```
  3. **拆分追加**: 把大内容拆成 5-10KB 一段, 多次 write_file + edit_file 追加
  4. **直接 Python append**: `with open('v7.js', 'a') as f: f.write(js_chunk)`
- **未来策略**: 任何超过 5KB 的 shell heredoc 都不安全, 改用 Python 追加或 write_file 写新文件

#### 关键教训 58: 多文件拆分策略的协调成本
- **问题**: 把 CSS 拆到 `v7.css`, JS 拆到 `v7.js`, 数据拆到 `v7_data.json`, HTML 拆到 `gen_html.py` 各自管理
- **代价**:
  1. 跨文件引用关系需要 HTML 加载多个 `<link>`/`<script>` 标签, 加载顺序重要
  2. 文件间数据传递需要 JSON.stringify/parse, 增加复杂度
  3. 任何文件修改都要重新生成 HTML 入口
  4. 调试时跨文件跳转让 stack trace 不直观
- **最佳实践**: 
  - **数据** (< 50KB): 放独立 .json 文件
  - **CSS** (> 5KB): 可放独立 .css 文件或内联在 HTML `<style>` 中
  - **JS** (> 10KB): 拆成几个独立 .js 文件按依赖顺序加载
  - **入口 HTML**: 保持小 (模板 + `<link>`/`<script>` 引用)

#### 关键教训 64: 检测 JS 括号平衡时, 字符串转义是头号干扰
- **问题**: 状态机对 `'\\n'` (4字符: `'\\n'`) 的处理: 1 个 `\\` 当作转义, 剩下 `n'` 视为未闭合字符串
- **真正的 JS 语义**: `'\\n'` 实际是字符串 `'\n'` (单字符 `\n` 在 JS 中就是字面 `\n` 2 字符, 但作为文件内容是 `\\n` 4 字符)
- **正确的状态机逻辑**:
  - 读取到 `\\` 时: 这 2 个字符是**一个** JS 转义序列, 应跳过这 2 个字符
  - 读取到 `'` 时: 闭合字符串 (但已经跳过了 `\\`, 所以下一个字符 `n` 在字符串内)
  - 读取到 `'` 时: 再次闭合? (错! 应该已经闭合)
- **本轮状态机错误**: 把 `\\` 当作一个反斜杠转义, 实际上状态机只看到 1 个 `\`, 然后下一个 `\` 又被当作转义起点
- **正确算法**:
  ```python
  if in_str and ch == '\\':
      j += 2  # 跳过 2 字符 (\\)
      continue
  if in_str and ch == in_str:
      in_str = None  # 闭合
  ```
- **目前**: 即使状态机不完美, 简单行级检查 (用 `count('(')` vs `count(')')`) 也可能更可靠 — 跳过字符串内容, 只统计"代码"部分

### 🔑 关键教训 102: file:// 协议 query string cache-bust 不可靠
- **场景**: 改完 HTML 文件, `navigate(url?v=2)` 后 evaluate 仍跑旧代码
- **表现**: `document.documentElement.outerHTML` 返回旧版, 报错指向已修复的函数
- **根因**: file:// 没有 HTTP cache 机制, 但浏览器历史/BackForward cache 可能保留
- **可靠方案**:
  1. `browser_use close` + `browser_use open` (新 page_id)
  2. 或 `?v=` + Ctrl+F5 强制刷新 (在用户手动操作时)
  3. 验证方法: `document.documentElement.outerHTML.indexOf('新代码锚点')` 必须 > 0
- **未来策略**: 任何结构性 HTML 大改后, 必走 close → open → evaluate 三步

### 🔑 关键教训 103: nested overflow-y:auto 在 flex column 中互相冲突
- **症状**: 父 flex column 子节点都设 overflow-y:auto, 子节点内容仍被裁切
- **根因**: 父 flex 容器的高度/收缩由内容决定 (content-sized), 而不是固定高度
- **正确模式**:
  ```html
  <!-- 父: 只设 flex 方向 + 高度, 不设 overflow -->
  <div style="display:flex; flex-direction:column; height:400px;">
    <div style="flex-shrink:0">固定头部</div>
    <div style="flex:1; overflow-y:auto; min-height:0">滚动内容</div>
  </div>
  ```
- **反模式**:
  ```html
  <!-- 父 + 子都 overflow-y, 父高度失效 -->
  <div style="display:flex; flex-direction:column; height:400px; overflow-y:auto;">
    <div style="flex-shrink:0">头部</div>
    <div style="flex:1; overflow-y:auto">内容</div>
  </div>
  ```
- **未来策略**: flex column 布局中, 只有**最内层**可以 overflow-y:auto; 中间层必须用 flex:1;min-height:0 让出滚动空间

#### 关键教训 122: 承认"部分字段被忽略"比"假装都生效"重要
- **原则**: 字段设计 → 字段编辑 → 字段拼装 → 最终 prompt，**链路必须完整**
